## 1. What the client sees when רלוונטי is blocked

**The button is disabled before it can be tapped, with the reason shown under it.**
- When a price change for that professional is waiting for an answer, their row on the review
  card shows **רלוונטי** greyed out and not tappable. Under it, one line says a price change is
  waiting for an answer: "ממתין לתשובה על שינוי המחיר" when the client is waiting on the pro,
  "ממתין לתשובתך על שינוי המחיר" when the pro is waiting on the client.
- The client never taps and then sees `price-change-pending` as an error. That server refusal
  remains only as the backstop for a race: a request arrives in the moment between render and
  tap. For that case the card shows the same sentence as a toast, never the code.
- The other two actions stay available. לא רלוונטי always works. שינוי מחיר is disabled with
  the same reason, because one change per role can be pending, and for a single-role pro that is
  the same condition.

**Does (c) need to supply anything beyond error mapping? No.** The card computes the disabled
state from what already exists:
- `listenToPaymentRequests(projectId, clientId)` (`src/features/chat/services/paymentService.ts`)
  already streams every **pending** request where the client is `from` or `to`.
- Every request on a project is between the client and one professional, so this covers every
  pending request on the project that involves the client.
- The card filters it by `professionalId`. **Any role counts**, which is exactly the key the
  server lock uses (`confirmCandidate` refuses on any pending request for that pro). The two
  cannot disagree.
- The direction for the reason text is `fromUserId === clientId`.

Step (d) wires that listener into the card. No server change is needed.

## 3. What changed

**`functions/src/lifecycle/priceRequestPolicy.ts` (new, pure)**
- `decideNewPriceRequest` is **one check** for both rules:
  1. Anything pending for this (pro, role), in either direction → `price-change-pending`.
  2. The caller is the client → allowed.
  3. The caller is the pro and the role is not under review → allowed (unchanged behaviour).
  4. The caller is the pro and the role is under review → allowed only if the **latest** client
     request for this role was **rejected** and the pro hasn't countered it yet. Otherwise
     `counter-not-allowed`. That means one counter **per client proposal**, as you confirmed.
- **Role:** `bundle:<id>` (a bundle is repriced as one unit), else `category:<name>`. A legacy
  request with neither matches every role.
- **History is sorted by `createdAt`, not array position.** Firestore returns documents in id
  order.

**`createPaymentRequest`**
- `isOfferPriceValid` (1–50000), otherwise `offer-price-out-of-range`. This replaced the
  `> 0` check.
- `underReview` is read from the same accepted offer or bundle doc that supplies `currentAmount`.
- The history query, the decision, the request write and the chat notice all run in **one
  transaction**, with the history read through `tx.get`.

**`respondToPaymentRequest`:** on accept, `isOfferPriceValid(newAmount)`, otherwise
`offer-price-out-of-range`. This replaced `< 0`. It covers requests created before the check.

**Rules:** see §2.

**Client:**
- `src/features/chat/utils/repriceErrors.ts` maps every refusal to a translation key.
  `project-details.tsx` uses it on both create and respond; before, respond had a bare catch.
- New keys in en and he: `project_details.reprice_out_of_range`, `reprice_pending`,
  `reprice_counter_not_allowed`.
- **Deviation from the plan:** the range message on *create* is a new key.
  `chats_page.hire_price_invalid` says the amount "can't be accepted", which is wrong when
  sending. It is still used for the accept path, where it is right.
- `project-details.tsx` already used `Alert.alert` in these two handlers. I only changed the
  message. This is not new UI. The step (d) card will use `confirmDialog` / toasts as you
  specified.
