## 1. The rules change, for your review before it goes live

Two changes to `firestore.rules`, both about the project `status`:
- **Update:** a client can no longer move a project INTO `in_progress`. Moving
  `in_progress -> open` (reposting a role) is still allowed. The terminal rules for
  `completed` and `cancelled` are unchanged.
- **Create:** a client can only create a project whose `status` is `open` (or absent,
  which reads as `open`).

## 2. What was built

**`functions/src/lifecycle/review.ts` (new)**
- **`isPendingReview(offer)`:** `status === 'accepted' && review === 'pending'`. It's the only
  definition on the server.
- **`decideActivation(project, offers)`:** pure. Activates only when all of these hold:
  - `status === 'open'`
  - no vacant seat (C3)
  - at least one accepted offer
  - nothing passes `isPendingReview`
- **Query helpers:** `acceptedOffers` / `pendingReviewOffers`.
- **`warnIfCompletedUnderReview`:** the C6 log. It never throws.

**`functions/src/lifecycle/candidates.ts` (new), exported:**
- **`confirmCandidate`:** client only. Refuses with `not-under-review`, or with
  `price-change-pending` while a price change for that pro is open. Sets
  `review: 'confirmed'` and `reviewedAt`, then runs `maybeActivateProject`.
- **`rejectCandidate`:** client only, and only while the pro is under review.
  - Refuses with `engagement-not-open` unless the fee doc's `engagementStatus` is `hired` (C6).
  - Runs `releaseEngagement(..., 'candidate_rejected')`.
  - Closes that pro's pending price changes.
  - The reason (at most 500 chars) goes by `sendBamaSystemDM`. If the DM fails, the release
    stands and the result says `dmSent: false`.
  - Then runs `maybeActivateProject`.
- **`maybeActivateProject`:** a transaction, with all reads before any write. Sets
  `status: 'in_progress'` and posts `🎬 הצוות נסגר: <names>` plus unread counts. Idempotent.

**Other server files**
- **`derive.ts`:**
  - **C1:** `deriveProjectState` ignores `candidate_rejected` engagements.
  - **C5:** `splitWithdrawals` / `withdrawalCount` return `candidateRejections` separately and
    leave them out of `withdrawn`.
- **`completion.ts`:** C6 `warnIfCompletedUnderReview` after both completion paths. It is awaited
  so the log isn't lost when the function returns.
- **Types:** `ReleaseReason` gains `candidate_rejected` (server `helpers.ts`, client
  `project.ts`), and `releaseEngagement` takes it.

**Client mirror**
- `src/features/chat/utils/review.ts`: `isPendingReview`, with the same rule as the server. The
  step (d) card listener must use it.

**The stale-flag filter is applied in both places you asked for**
- the server activation rule (`decideActivation` → `isPendingReview`);
- the client helper the card will use.

A rejected pro's offer becomes `removed` but keeps `review: 'pending'`, and neither place counts it.

## 4. Report, not fixed: a sole professional WITHDRAWING marks the project `completed`

**The problem**
- `deriveProjectState` treats "every engagement terminal" as complete, including when every
  engagement is `withdrawn` (`pro_withdrew`, or `client_removed` through an accepted removal).
- `applyDerivedProjectState` then sets `status: 'completed'`, `completedAt` and `slotHolders: []`.
- Nothing lets the client back out of that:
  - the rules forbid a client leaving `completed`;
  - `canHireOnStatus` refuses new hires;
  - there is no reopen callable.
- **Result:** the client has to create a new project to replace someone who left before doing
  any work.
- The existing test `completes a project where EVERYONE withdrew` pins this as deliberate. Its
  reasoning ("nothing more will happen on it") holds only if the client doesn't want a
  replacement.

**Live exposure right now (read-only production scan):** 6 projects are `completed`, and **0** of
them have nobody who delivered. Nobody is stuck today, but any single-pro project where the pro
withdraws will be.

**Options**
- **A (recommended).** Treat "every engagement terminal and **none delivered**" (all `withdrawn`
  or `cancelled`) as **not** complete.
  - The project stays `open` and its seats are vacant again, exactly like the C1 path.
  - Mixed projects, where someone delivered, still complete as today.
  - Small change in `deriveProjectState` plus the existing test's expectation.
  - One consequence: such a project reappears on the noticeboard. For a client who wants a
    replacement that's the point, and a client who doesn't can cancel.
- **B.** Keep completion, and add a client `reopenProject` callable limited to projects where
  nobody delivered. More surface: a callable, UI and rules reasoning.
- **C.** Leave it as it is.
