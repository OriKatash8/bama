## 5. Where the test suite had gaps (your request)

**Across V1, exactly two mutations survived the unit tests that already existed.** Each was only
caught after I added or rewrote a test:

1. **Step (c), R5: price-request history not sorted by time**
   (`priceRequestPolicy.ts`, removing `.sort((a,b) => a.createdAtMs - b.createdAtMs)`).
   - **Why it survived:** the "orders by time" test had a history whose array order and time order
     happened to give the same answer.
   - **The fix:** rewrote the test so a counter listed *before* the proposal it answered (the order
     Firestore returns by doc id) must still count.
   - **Why it matters:** without sorting, a pro could counter twice whenever doc ids came back out
     of time order.
2. **Step (d), D13: `useUserBasics` treating a missing or blank user as resolved**
   (returning `{ displayName: '' }` instead of `null`).
   - **Why it survived:** every card test mocks `useUserBasics`, so nothing exercised the hook's own
     "no identity → null" rule. That rule is what keeps the row's buttons locked.
   - **The fix:** added `useUserBasics.test.tsx`.
   - **Why it matters:** a missing user doc would have shown a blank name with a live רלוונטי,
     which is exactly the "confirm the wrong person" case you asked to block.

**Two similar gaps, recorded so they aren't miscounted:**
- **Step (c): the emulator concurrency probe couldn't see the bug.** With the history read moved
  outside the transaction it still passed, because the shared chat-doc write serialized the two
  creates anyway. §4b was added with no chat doc, and then the broken build let both requests
  through in 2/2 runs. This was a probe gap, not a unit-test survivor.
- **Step (d): the writing-direction bug was found in the browser, not by a surviving mutation.**
  No test existed for it until after the fix. The (d) report listed it among the "survived" ones;
  that wording was loose, and it is corrected here.
