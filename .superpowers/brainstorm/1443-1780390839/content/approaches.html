Three Approaches to Dual-Mode Architecture

How the routing and mode-switching are structured under the hood

A

Navigate-on-Switch (Recommended)

Keep the two existing route groups (client)/ and (professional)/. Add a mode-picker screen shown at app launch. When the user switches mid-session, a router.replace() jumps to the other group's default screen. Mode lives in the Zustand auth store.

Pros

  • Least code change — route groups stay as-is
  • Clean separation between modes
  • Familiar pattern in existing codebase

Cons

  • Switching resets tab state (you land on the default tab)
  • Two tab bars to maintain
B

Single Dynamic Layout

Collapse both route groups into one (app)/ group. The tab bar reads activeMode from Zustand and renders different tabs. Switching mode updates the store; the tab bar re-renders instantly with no navigation.

Pros

  • Smoothest UX — instant mode switch, no navigation flash
  • Single tab layout to maintain
  • Shared screens (bookings) appear in both modes naturally

Cons

  • Most refactoring — routes, layouts, and screens all change
  • Conditional tab logic adds complexity
C

Mode Gate Route Group

Add a new (mode-gate)/ route group between auth and the main app. Once a mode is picked, it's stored in AsyncStorage so it's remembered for the session. Keep the two route groups but guard them with the stored mode.

Pros

  • Cleanest conceptual separation — you "enter" a mode
  • Mode persists through backgrounding the app

Cons

  • More route groups to manage
  • Mid-session switching still requires a hard navigate
  • AsyncStorage adds unnecessary complexity for a session choice

My recommendation is A — it matches the existing patterns in your codebase, requires the least structural change, and the hard-navigate on mode switch is actually fine UX for a marketplace app where switching contexts means a completely different set of tasks.
